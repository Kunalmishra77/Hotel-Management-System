# 23 · Booking Engine — Requirements

> Source: client doc §19 (Future Expansion — public direct online booking). Read with `.claude/rules/api-conventions.md` (public route handlers, rate-limit, webhooks), `security.md`, `integrations.md` (payments sandbox↔live), `business-rules.md` (availability, folio, GST), `compliance.md` (DPDP consent, PII), `prisma/schema.prisma`. Depth bar: `specs/03-reservations/*`.

## Purpose & scope
A **public, unauthenticated, mobile-first** booking website where a prospective guest searches availability and rates for a property and completes a **direct online booking** that pays a deposit (or full amount) through a payment gateway and results in a **CONFIRMED reservation with source `WEBSITE`** created via module 03, a folio and advance payment recorded via module 06. All guest-facing traffic runs through **rate-limited, bot-protected public route handlers** under `/api/booking-engine/v1/*`; going live on payments is a config change gated on client KYC.

**In scope:** public property/rate/availability display (online-sellable inventory only), a book-and-pay checkout flow (search → select → guest details + consent → temporary inventory hold → gateway payment → confirm), payment-webhook-driven confirmation, guest self-service lookup/cancel via signed link, booking-engine configuration (deposit/cancellation/stay policies, gateway selection), rate limiting + bot/abuse protection, graceful degradation to sandbox gateway and base-rate fallback.
**Out of scope:** reservation lifecycle mechanics, availability truth, holds/confirm/cancel internals (03 — this module *calls* 03); folio ledger math, GST invoice, refund mechanics (06); dynamic rate **computation** (24 — this module *consumes* a resolved rate); OTA/channel sync (13); messaging provider mechanics (12); staff-facing booking UI (03).

## Dependencies
- **Tier 0:** 00-platform (domain events, audit, `IntegrationInbox`, pg-boss jobs, object storage, request-id/observability), 01-property-management (property public profile, GSTIN, timezone), 02-room-inventory (`RoomCategory`, `Room`).
- **Tier 1:** 03-reservations (`searchAvailability`, `holdReservation`, `confirmReservation`, `cancelReservation`, `reallocateRoom` for FR-8 equivalent-room), 04-guest-crm (guest upsert + duplicate detection on mobile/email).
- **Tier 2:** 06-billing-payments (`ensureFolio`, record advance `Payment` via `recordPayment`, `refund` for the FR-16 windowed cancel of a **confirmed** booking) + `PaymentProvider` gateway adapter (its `refund` handles the FR-8 auto-refund of an **unconfirmed** deposit, where no folio exists yet).
- **Tier 5 peers / consumers:** 24-dynamic-pricing (resolved sellable rate), 12-communications (confirmation/receipt), payments **live** (client KYC).

## Data owned
Owns **`BookingEngineConfig`** (per-property online-booking settings) and **`BookingEngineOrder`** (gateway-order ↔ held-reservation binding + consent snapshot) — both **confirmed present in canonical schema** (migration materializes the slice; nothing new). Reads: `Property`, `RoomCategory` (incl. `gstBps` for GST-inclusive display), `Room` (availability via 03 queries), resolved rate via 24. Writes **through other modules' public surfaces**: `Reservation`/`RoomAllocation` (03), `Guest` (04), `Folio`/`Payment` (06), `IntegrationInbox`/`DomainEvent`/`AuditLog` (00). This module performs **no foreign SELECTs** into other modules' tables.

## Functional requirements (EARS)
- **FR-1 (ubiquitous):** Expose a **public, unauthenticated, versioned** route-handler surface `/api/booking-engine/v1/{slug}/*` keyed by a property's public slug; no session/cookie is required to search or book.
- **FR-2 (ubiquitous):** Surface **only** properties and room categories flagged `onlineSellable` in `BookingEngineConfig`; never expose non-sellable inventory, internal room numbers (pre-confirmation), rates for hidden categories, staff data, or any other guest's PII.
- **FR-3 (event):** When a guest requests availability for a date range + occupancy, return per-**category** availability count and the **resolved sellable rate** — via `24.resolvedRate({categoryId, date, negotiatedRatePaise?})` (public/anonymous bookings pass no `negotiatedRatePaise`) — computed against the **single availability truth in 03** (cancelled/no-show excluded, others' live holds excluded), with a **GST-inclusive display price** using `RoomCategory.gstBps` (config-driven room GST slab, in canonical schema).
- **FR-4 (event):** When a guest submits guest details for a chosen category, upsert a `Guest` via 04 (duplicate detection on mobile/email) and place a **temporary inventory hold** via 03 `holdReservation` (`ENQUIRY`, source `WEBSITE`) for a configurable **checkout TTL** (default 15 min).
- **FR-5 (event):** When a hold is placed, create a **payment order** via 06/`PaymentProvider` for the deposit amount per `BookingEngineConfig` deposit policy (full | percentage | fixed) and persist a `BookingEngineOrder` binding `gatewayOrderId` ↔ held reservation ↔ amount ↔ **client idempotency key**; return only gateway params the client needs.
- **FR-6 (event):** When the gateway posts a webhook to `/api/webhooks/payments/{provider}`, **verify the provider signature before any processing** and dedupe via `IntegrationInbox` on the provider event id (`integrations.md`).
- **FR-7 (event):** When a verified **payment-success** webhook is processed, in **one transaction**: confirm the held reservation via 03 (→ `CONFIRMED`, `ensureFolio`), record the advance `Payment` via 06, mark the `BookingEngineOrder` `PAID`, emit `WebBookingConfirmed`, and trigger the guest confirmation via 12.
- **FR-8 (unwanted):** If a payment succeeds but the hold has **expired** or the room is no longer available, then do **not** overbook — attempt re-allocation to an equivalent room in the same category via `03.reallocateRoom(reservationId)` (`toRoomId` omitted → 03 auto-picks a free room in the same category); if none is free, initiate an **automatic refund via `PaymentProvider.refund`** (the gateway adapter — the booking never confirmed, so there is no folio and 06 is not involved) and notify the guest that the booking failed and money was returned.
- **FR-9 (unwanted):** If payment fails, is abandoned, or the checkout TTL elapses, then **release the hold** via 03 (inventory returns to sale), mark the order `FAILED`/`EXPIRED`, and **never confirm**.
- **FR-10 (ubiquitous):** Enforce **per-IP + per-route rate limits** on every public endpoint; exceeding a limit returns **429** with `Retry-After` and produces **no** hold/order/reservation side effects.
- **FR-11 (unwanted):** If bot/abuse signals fire (captcha failure, honeypot field filled, velocity/anomaly threshold), then reject **before** any hold/order is created and write an audit record of the attempt.
- **FR-12 (event):** When a booking is submitted, capture **explicit DPDP consent** and terms/cancellation-policy acceptance (policy version + timestamp) on the `BookingEngineOrder`; a booking cannot confirm without recorded consent.
- **FR-13 (state):** While a hold is active (`ENQUIRY`, `holdExpiresAt` in the future), the held inventory is **unavailable to all other online and direct bookings identically** — one availability truth (`business-rules.md` §1–3).
- **FR-14 (unwanted):** If requested dates/occupancy violate config constraints (min/max length-of-stay, lead-time window, max rooms per booking, occupancy over category max without an allowed extra bed), then reject at validation with a clear message; **nothing persists**.
- **FR-15 (ubiquitous):** Compute and present all prices in paise→₹ with GST per `business-rules.md` §10–13; the **amount charged equals the displayed total** — no client-side recomputation that can diverge (`business-rules.md` §21).
- **FR-16 (event):** When a guest opens a **signed booking-reference link** (no login), verify the signed token, show status, and allow **guest-initiated cancellation** only within the configured cancellation window — delegating to 03 `cancelReservation` and the 06 refund policy.
- **FR-17 (ubiquitous):** Every server-side booking-engine mutation (hold, order, confirm, cancel, refund, config change) **emits a domain event and writes an audit record** with request id, ip, and device (`business-rules.md` §20). The public book/pay flow is unauthenticated, but **staff-facing `BookingEngineConfig` changes** (deposit/cancellation/stay policies, gateway selection, publish) require the `bookingengine:manage` permission (per `rbac-matrix.md`, 🔒 audited).
- **FR-18 (unwanted):** If the payment gateway has no live credentials it runs in **sandbox/mock** and still completes end-to-end (non-prod); if a resolved dynamic rate is missing, fall back to `RatePlan`/`RoomCategory.baseRatePaise` — the search **never fails** for a missing rate (`integrations.md`).
- **FR-19 (state):** While a `BookingEngineOrder` is `CREATED` (awaiting payment) the booking is **not** confirmed and the hold governs inventory; order processing is **idempotent** under webhook retries (dedupe on `gatewayOrderId` + provider event id).
- **FR-20 (ubiquitous):** Public responses expose no PII of other guests, no internal room numbers before confirmation, and no secrets; a guest can read only their **own** booking via the signed link.
- **FR-21 (event):** When `WebBookingConfirmed` is emitted, module 14 counts it in `WEBSITE`-source revenue/pace and module 12 sends the confirmation — the booking engine **does not poll**; consumers react to the event.
- **FR-22 (unwanted):** If a duplicate submit (double-tap / retried POST) reuses the same **client idempotency key**, then return the original result without creating a second hold/order/reservation.

## Non-functional (cited)
Availability search p95 **< 500ms**; hold/order create p95 **< 800ms**; public site first meaningful interaction **< 2.5s** cold on a mid-range phone over 4G; **no overbooking under concurrency** (correctness > availability on the booking path); **rate-limit** all public + webhook endpoints; integration failures **degrade gracefully** to sandbox/mock; India data region. (`rules/non-functional-requirements.md`, `security.md`.)
