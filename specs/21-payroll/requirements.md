# 21 · Payroll — Requirements

> Source: client doc §19 (Future Expansion — payroll). Built now (see `rules/scope.md`). Read with `.claude/rules/business-rules.md` (money §8, cross-cutting §20), `rules/data-model.md` (money/time), `rules/non-functional-requirements.md`, `prisma/schema.prisma` (models `PayrollRun`, `PayrollLine`, `Staff`, `Attendance`). Depends on module **09-staff-management** for the source records.

## Purpose & scope
Turn each property's `Staff` records and their `Attendance` for a calendar month into a reviewable, finalizable **payroll run**: one `PayrollLine` per eligible staff member with `base`, `advance`, `bonus`, `deduction`, `overtime`, and `net` (all paise), then generate a payslip per line. Owns the payroll computation and the DRAFT→FINALIZED run lifecycle.

**In scope:** monthly run creation per property; deterministic computation of base (attendance/joining-pro-rated), overtime (from `Attendance.overtimeMinutes`), and net; per-line capture of advance recovery / bonus / manual deduction; DRAFT editing + audited overrides; finalize (lock + immutable); payslip PDF generation; exposing finalized staff cost to reporting/accounting via events; masking of staff bank/PII.
**Out of scope:** staff records & attendance capture (09-staff-management — this module only reads them); statutory PF/ESI/PT/TDS engines (v1 records these as manual deduction components — auto-computation proposed in Schema notes); disbursement/bank-file generation and the accounting journal (22-accounting-sync consumes the finalize event); expense ledger entry mechanics (07-expenses).

## Dependencies
- **Tier 0:** 00-platform (auth, tenancy, events, audit, object storage, pg-boss), 01-property-management.
- **Tier 2 source:** 09-staff-management (`Staff`, `Attendance`) — read **only** through its query layer, `getStaffForPayroll(propertyId, month)` on the write path (FR-17).
- **Downstream consumers:** 07-expenses / 08-profit-reports (staff cost), 14-dashboard-analytics, 22-accounting-sync (salary journal). None are called synchronously on the write path; they consume `PayrollFinalized`.

## Data owned
`PayrollRun` (id, propertyId, month `"YYYY-MM"`, `sequence`, `runType`, status, lines), `PayrollLine` (basePaise, advancePaise, bonusPaise, deductionPaise, overtimePaise, netPaise). **Reads — computation inputs via 09 `getStaffForPayroll`:** `Staff` (monthlySalaryPaise, joinedOn, leftOn, isActive) + raw `Attendance` (day, isLeave, leaveType, overtimeMinutes, workedMinutes), plus `Property` (timezone, day basis); bank/masked-PII for payslips comes from 09's permissioned masked read, not this payload (FR-16). All of these are **confirmed present in canonical schema** — `PayrollRun.finalizedAt/finalizedById/netTotalPaise`, `PayrollRun.sequence/runType`, `PayrollLine.payslipObjectKey/paidDays/lopDays/otMinutes/notes/createdAt`, `PayrollRunStatus` enum, `StaffAdvance` (incl. `recoveredPaise`), `Attendance.leaveType` (`LeaveType`) — a migration materializes the slice, nothing is new.

## Functional requirements (EARS)
- **FR-1 (ubiquitous):** Represent each month's **regular** payroll as exactly one `PayrollRun` with `sequence = 1`, `runType = "REGULAR"` per `(propertyId, month)` (month = property-local `"YYYY-MM"`), holding one `PayrollLine` per eligible staff member. Separately-audited **adjustment** runs for the same month carry `sequence > 1` / `runType = "ADJUSTMENT"`; the `@@unique([propertyId, month, sequence])` key permits them (FR-8).
- **FR-2 (event):** When a run is generated for `(property, month)`, read eligible staff + raw per-day attendance via **09 `getStaffForPayroll`**, compute each member's `basePaise` and `overtimePaise`, **seed `advancePaise` from the outstanding `StaffAdvance` balance** (`Σ (amountPaise − recoveredPaise)` per staff), seed `bonusPaise/deductionPaise` from suggested defaults, persist DRAFT lines in one transaction, and emit `PayrollRunGenerated`.
- **FR-3 (ubiquitous):** Compute `basePaise = roundHalfUp(monthlySalaryPaise × paidDays ÷ daysInBasis)`, where `paidDays = min(employedDays − lopDays, daysInBasis)` — **capped at `daysInBasis`** so a full or over-attended month never pays above basis — `employedDays` = calendar days of the month the staff is employed (from `max(monthStart, joinedOn)` to `min(monthEnd, leftOn ?? monthEnd)`), and `daysInBasis` is config `PAYROLL_DAY_BASIS` (default = calendar days in the month). **21 is the single authority for `employedDays`** (09 supplies the raw dates; it does not compute the pay basis). `lopDays` is derived per FR-18.
- **FR-4 (ubiquitous):** Compute `overtimePaise = roundHalfUp(totalOvertimeMinutes × ordinaryRatePerMinute × otMultiplier)`, where `ordinaryRatePerMinute = monthlySalaryPaise ÷ (PAYROLL_OT_DIVISOR_DAYS × PAYROLL_STANDARD_MINUTES_PER_DAY)` (defaults 26 days, 480 min/day) and `otMultiplier = PAYROLL_OT_MULTIPLIER` (default 2.0, per Factories Act §59), summing `Attendance.overtimeMinutes` over the month.
- **FR-5 (ubiquitous):** Compute `netPaise = basePaise + bonusPaise + overtimePaise − deductionPaise − advancePaise`, rounded per component to the paisa. **Ordering at the floor (FR-15):** earnings first, then **manual/statutory `deductionPaise` is applied in full**, then **advance recovery** takes only the remaining non-negative balance — deductions always rank ahead of advance recovery. The run total is Σ line `netPaise`.
- **FR-6 (state):** While a run is `DRAFT`, allow editing `bonusPaise`, `deductionPaise`, and advance recovery per line and re-deriving `basePaise/overtimePaise` from current attendance; every edit re-computes `netPaise`, writes an audit row, and emits `PayrollLineAdjusted`.
- **FR-7 (event):** When a run is finalized, lock the run and all lines (append-only thereafter), stamp `finalizedAt/finalizedById`, set status `FINALIZED`, emit `PayrollFinalized`, and generate one payslip PDF per line to access-controlled object storage.
- **FR-8 (unwanted):** If a finalized run or any of its lines is edited, deleted, or re-generated, reject it (`RUN_LOCKED`); corrections are made only via a **new adjustment run** for the same `(property, month)` at the next `sequence` (`runType = "ADJUSTMENT"`), separately audited — now possible under the `@@unique([propertyId, month, sequence])` key (the old `(propertyId, month)` key made this impossible).
- **FR-9 (state):** While a run is `FINALIZED`, its lines are immutable and read-only; payslips remain downloadable by authorized roles.
- **FR-10 (unwanted):** If a **regular** run (`sequence = 1`) is generated for a `(property, month)` that already has one, do not create a duplicate — return the existing `DRAFT` run for review, or reject with `RUN_EXISTS` if it is `FINALIZED` (a correction then goes through a new adjustment run per FR-8, not a re-generation).
- **FR-11 (ubiquitous):** Exclude from the run any staff not employed during the month — `joinedOn` after month end, or `isActive = false`/`deletedAt` set before the month start.
- **FR-12 (event):** When a run is finalized, expose the aggregate salary cost to profit/expense reporting and accounting via `PayrollFinalized` (async consumers: 07/08/22); 08 also **pulls** it synchronously via `getFinalizedStaffCost(propertyIds, range)` (sum of finalized runs' `netTotalPaise` per `(property, month)` in range — the canonical read, no foreign SELECT). The same cost is never counted twice — payroll is the single source of the STAFF salary cost, never also hand-keyed as a 07 expense.
- **FR-13 (unwanted):** If a derived component (`basePaise`/`overtimePaise`) is manually overridden away from its computed value, require permission `payroll:run` **plus** a reason and write an audited override; otherwise reject.
- **FR-14 (ubiquitous):** Every payroll mutation is property-scoped, authorized server-side (`payroll:run`, 🔒 audited per `rbac-matrix.md`), audited, and emits its domain event (`business-rules.md` §20).
- **FR-15 (unwanted):** If `netPaise` would go negative, floor it at 0: apply `deductionPaise` first, then recover only the **affordable portion** of the advance (`recovered = min(advanceOutstanding, remainingAfterDeductions)`); increment that staff member's `StaffAdvance.recoveredPaise` by exactly `recovered`, and **carry the un-recovered shortfall forward** — the next month's run re-seeds `advancePaise` from the still-outstanding `StaffAdvance` balance (`amountPaise − recoveredPaise`, per FR-2). Never disburse a negative amount.
- **FR-16 (ubiquitous):** Expose staff bank details / masked Aadhaar/PAN on lines and payslips only to authorized roles; mask by default in lists and exports (`compliance.md`).
- **FR-17 (ubiquitous):** Read `Staff` and `Attendance` only via module 09's query layer — `getStaffForPayroll` on the write path (raw per-day attendance), `attendanceSummary` for context; never issue foreign SELECTs into another module's tables (`data-model.md`).
- **FR-18 (unwanted):** Derive `lopDays` from each employed day's attendance by `leaveType`: a day with `leaveType = UNPAID` counts as **LOP**; `PAID`/`CASUAL`/`SICK` leave and normal worked days are **paid** (not LOP). For an employed day with **no attendance record**, behavior is config-explicit: `PAYROLL_ABSENCE_IS_LOP` off (default) → paid (do not auto-dock); on → LOP. An explicit `UNPAID` day is **always** LOP regardless of the flag — closing the prior gap where only missing days could become LOP and an explicit unpaid day was wrongly paid.

## Non-functional (cited)
Run generation and finalize server actions p95 < 800ms for a property of ~100 staff; payslip PDF renders < 3s (mirrors the invoice budget, `non-functional-requirements.md`); all money in integer paise via Decimal.js, round half-up at component level; review/finalize usable on a phone; computation deterministic with an injected clock for tests.
